The CPU waits for memory

The memory hierarchy

  • Add two floats: < 1 ns. Fetch from RAM: ~100 ns.
Level Size Latency If L1 = 1 s
registers ~100s B ~0 instant
L1 32–64 KB / core ~1 ns 1 s
L2 256 KB–1 MB ~4 ns 4 s
L3 8–32 MB ~15 ns 15 s
RAM 16–64 GB ~100 ns ~2 min

While waiting, the core could have done hundreds of operations. This machine: L1d 544 KiB total (14 instances), L2 18 MiB total (9 × 2 MiB instances, not one core’s cache), L3 24 MiB shared. Hybrid CPU (P/E/LP-E cores) — per-core L1 differs, hence “instances”. lscpu shows it; the script asks students to compare with their own.

Caches bet on locality

  • Temporal: used now → used again soon.
  • Spatial: used now → neighbors next.
  • Memory moves in lines of 64 B = 8 Float64.

Why 6.5×? Throughput vs latency

  • Latency: the wait for one unpredictable access (the table).
  • Our loop reads in order → hardware loads the next lines early.
  • We pay for the bandwidth (throughput), not for each wait.

100× is real when the next address is unpredictable (linked list, random indices).

Not “the table is wrong” nor “machine noise”. The part of the hardware that loads lines early is the prefetcher. Latency and bandwidth are different resources; a streaming sum is bandwidth-bound, a linked-list walk is latency-bound. The same pair comes back with batching: time per request vs examples per second.

A5 — debrief: batching, measured on the CPU

W = 64 MiB. One by one (W * x): 1090 µs / example.

B total µs / example vs one by one
1 2.55 ms 2551.8 0.4×
8 5.65 ms 706.0 1.5×
64 11.06 ms 172.9 6.3×
256 39.06 ms 152.6 7.1×
1024 141.80 ms 138.5 7.9×

Compare with your table (4 MiB W). Same gain? Explain why.

B=1 here is a one-column matrix product (W * X[:,1:1]), slower than a true matrix-vector product (2.55 vs 1.09 ms): a lot of one is not the reference, and it is not free. Against the B=1 row of this table the ratio would read 18.4×; against the honest one-by-one reference it is 7.9×. Quote 7.9×. Activity with a 4 MiB W: do NOT expect the gain to vanish. On a test machine (1 BLAS thread) it was still ~9× at B=64: W no longer streams from RAM, but it does not fit in L1/L2 either, and one call per example pays its own overhead. Several mechanisms, one ratio: the honest debrief is “which measurement separates them?” — vary m, vary BLAS threads. numpy (python/4) gives almost the same numbers as Julia on the 64 MiB case.

Why B = 1024 barely helps any more

2551.8 → 172.9 (B=64) → 152.6 (B=256) → 138.5 µs: flattens.

  • W = 64 MiB > 24 MiB L3: a fixed RAM stream per lot.
  • Batching divides it by B:

\[\text{time per example} \approx \text{compute} + \frac{\text{stream } W}{B}\]

  • B ≈ 256: second term tiny.

The 1/B model fits: 138.5 µs ≈ pure compute per example; 2551.8 ≈ that plus the whole W stream. This is why python/4 uses n=4096: at 2000² W (16 MB) fits in L3 and the mechanism disappears.

A bigger batch is not always better

  • Throughput: examples per second. Grows with B, then flattens.
  • Latency: one request waits for the 63 others of its lot.

Choose B for the objective: overnight job or interactive service?

Same pair as earlier today (one access vs a stream). Last question of the activity. For the project: state which of the two you optimize.

What we keep

  • Neighbors are cheap, jumps are not.
  • Inner loop along contiguous memory: check your layout.
  • Batching reuses loaded data, even on a CPU.
  • Throughput and latency are different objectives.

C-order vs F-order arrays, 8000²:

numpy ratio why
A.sum(axis=0) ≈ 1× numpy reorders
copy F→C / C→C 13.2× (109.5 / 8.3 ms) source/destination layouts differ

numpy hides the layout cost; Julia shows it. Neither removes it.

On sum, someone wrote the reordering for you. A mismatched copy or a hand-written loop: the full penalty is back. Measured: sum(axis=0) C/F = 1.14× at 8000², 0.77× at 2000² — noise around 1×, and load-sensitive (0.45× seen under load). Don’t over-read either side of 1×. Demo lives in the Python notebook (python/4).

Allocating is memory traffic too

z = 2 .* x .+ y      # NEW 76 MiB array
z .= 2 .* x .+ y     # reuses z

▶ Script: cell “Optional — allocating is memory traffic too”

n = 10⁷ time allocated
z = … 54 ms 76 MiB
z .= … 17 ms 0 bytes

One dot: ~3×. But measure: the gain isn’t always there.

A new array is fresh memory to fetch and fill. Same for BLAS: A * B allocates, mul!(C, A, B) reuses C. At n = 2000 on this laptop the gain swings from no gain to ~3× from run to run (hybrid cores): measure. numpy gains only ~1.4× with out=: it can’t FUSE 2*x + y into one pass. For matrix × VECTOR the output is tiny and the gain vanishes. Measured at rest: mul!(y, W, x) on matrix-VECTOR was actually SLOWER than W * x (760 vs 468 µs). On the GPU, in place gains nothing in Julia either (2.10 vs 1.82 ms; CUDA.jl allocates from a pool) — whereas torch in place does gain (1.35 → 0.80 ms). The law is “allocation = memory traffic”.

Arithmetic intensity: FLOP per byte

n×n, Float64 FLOP bytes intensity
mat × vec 2n² 8n² 0.25 — constant
mat × mat 2n³ ~24n² ~n/12 — if each matrix crosses memory once
  • Low: compute waits for loads → memory-bound.
  • High: reuse can shift the limit toward compute.

To compare sizes, compare GFLOP/s, not seconds.

▶ Script: cell “Optional — arithmetic intensity”

Work per byte loaded; a FLOP = one + or *. Don’t compare seconds: they do different work. GFLOP/s = 10⁹ FLOP per second. The batching demo as throughput: 13.1 → 47.5 → 194.1 → 219.9 → 242.3 GFLOP/s for B = 1 … 1024. Intensity is per BYTE, not per value (8× apart for Float64) — be consistent. BLAS-3 (GEMM) tiling is what approaches reuse (ideal three-matrix Float64 traffic gives n/12 FLOP/byte): each tile is reused from cache.
