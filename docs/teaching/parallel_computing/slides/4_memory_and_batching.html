Memory and locality

The memory hierarchy

Level Typical capacity Typical latency
Registers < 1 KiB per core none
L1 32–64 KiB per core ~1 ns
L2 256 KiB–2 MiB ~4 ns
L3 8–32 MiB ~15 ns
RAM 16–64 GiB ~100 ns

The core looks in L1, then L2, then L3, then RAM. Smaller memories are closer to the core.

Indicative orders of magnitude, not specifications for every processor. Registers: x86-64 has 16 general-purpose 64-bit registers and 16 vector registers (256 bits with AVX2, as on the reference laptop). Cache sharing differs by level and core design. Reference laptop: 24 MiB shared L3; L1d 544 KiB in 14 instances, L2 18 MiB in 9 instances. Do not interpret aggregate cache sizes as a single core’s cache. Access latency is not the mean time per element in a streaming loop.

Who decides where data live?

  • Registers: the compiler. In s += a[i], the local variable s stays in a register.
  • L1, L2, L3: the hardware, automatically. No instruction says “keep this array in L2”.
  • You: indirectly, through access order, data size and reuse.

On a GPU, part of this is explicit: a fast on-chip shared memory is managed by the programmer.

When registers run out, the compiler “spills” variables to the stack, which in practice lives in L1. The compiler inspection of module 1 (optional section) shows the accumulator in a register (xmm/ymm). Expert hints exist but are out of scope: prefetch instructions, stores that bypass the cache, cache partitioning on servers. The two experiments of this deck act on access order and reuse. GPU (NVIDIA): registers per thread, shared memory per block of threads (explicit, e.g. CuStaticSharedArray in CUDA.jl), global memory = VRAM, plus automatic L1/L2 caches. Not used in this course. A warp is a group of 32 threads executing together, not a memory level.

Two forms of locality

Locality Practical idea Experiment
Spatial Use neighboring values Loop order
Temporal Reuse recently accessed values Batching

On the reference machine, a 64-byte cache line holds eight Float64 values.

A cache line is a transfer unit, not one individual array entry. Temporal reuse depends on working-set size and access order; merely repeating a computation does not ensure a cache hit.

Array size and processing rate

Reference observations on the course laptop:

Footprint Average ns / element
8 KiB 0.049
4 MiB 0.128
64 MiB 0.317

A larger working set changes the processing rate. These numbers are not individual access latencies.

Historical rounded BenchmarkTools minimum timings normalized by all processed elements. The reference L3 is 24 MiB. Cache capacity, prefetching, vectorization and other hardware behavior contribute. Do not assign every point to one cache level from timing alone.

Latency is not time per element

  • Latency: delay until one requested value is available.
  • Transfer unit: RAM sends a whole cache line (64 bytes) in one burst over the bus (the wires between RAM and the chip), a few bytes per step.
  • Processing rate: in an in-order scan, the CPU requests the next lines before they are needed, so the waits overlap.

Average time per element can be much smaller than access latency.

One wait of ~100 ns brings 8 Float64. At 64 MiB we measure 0.317 ns per element, i.e. ~25 GB/s for one core; with ~100 ns latency that needs ~2.5 KB, i.e. ~40 cache lines, in flight at once (rate × latency). The prefetchers keep that many requests going. Analogy: order many pizzas at once instead of waiting for each one; every delivery still takes 30 minutes (latency), but one arrives every minute (rate). Bus width depends on the memory type; the line is always 64 bytes. DDR4: 64-bit channel, 8 transfers per line. DDR5: 32-bit subchannels, 16 transfers. Reference laptop: LPDDR5 at 7467 MT/s, 8 channels of 16 bits, so 32 transfers of 2 bytes per line, ~120 GB/s peak over all channels. Do not confuse with a “64-bit processor”: that is the width of registers and addresses (a Float64 fits in one register). The CPU–GPU link of the GPU module (PCIe) is another link. Prefetching and multiple outstanding accesses can hide latency in a stream. A dependent pointer-chasing traversal is another experiment; random addresses alone do not necessarily prevent overlapping reads. Later, distinguish per-request latency from examples per second.

Experiment 1 — use neighboring data

Two loop orders, the same sum

Sum an 8000×8000 matrix, two loop orders:

# COLUMN by column
for j in axes(M, 2)
    for i in axes(M, 1)
        s += M[i, j]
    end
end
# ROW by row
for i in axes(M, 1)
    for j in axes(M, 2)
        s += M[i, j]
    end
end

Choosing the batch size

  • Throughput: larger batches can reduce time per example.
  • Latency: requests may wait for the batch to fill and finish.
  • Memory: larger batches need larger input/output buffers.

Choose the smallest batch that meets throughput and latency targets within the memory budget.

For offline work choose a batch near the best observed throughput without unnecessary buffers. The activity’s input/output payload per batch is a model, not a measurement of peak process RAM: the full dataset is already resident and concatenation also allocates memory. Queueing time is not measured by the matrix-product timer. An optional simplified model is t_example ≈ t_compute + t_load/B. It suggests amortization, but does not identify which term dominates or prove compute-bound execution.

Three practical choices

  • Follow the array’s memory layout.
  • Reuse data across computations.
  • Choose batch size by measuring throughput, latency and memory use.
