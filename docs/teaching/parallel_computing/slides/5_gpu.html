Device, data and measurement

Same operation, another array type

A = rand(Float32, 3, 3); B = rand(Float32, 3, 3)
Ag = CuArray(A); Bg = CuArray(B)   # copy to GPU memory, same dtype
A * B                            # CPU
Ag * Bg                          # GPU method

Dispatch selects an implementation from the argument types; the mathematical operation is unchanged.

▶ Script: cell “4. Device and precision”. RAM and GPU memory are separate here. CuArray(A) preserves A’s element type; the convenience function cu may narrow Float64 to Float32. Both copies and changes in precision must be stated. The GPU has many execution lanes, but a CUDA thread is not comparable to a CPU core. Small workloads may not amortize overhead.

Specify accuracy before comparing

  • Hold input values and dtype fixed for a deterministic comparison.
  • Check the result against a justified numerical tolerance.
  • For Monte-Carlo, also specify the statistical accuracy target.

A faster Float32 calculation is useful only if its accuracy meets the requirement.

The default dtype can differ across libraries. FP32, FP64 and accelerator math modes may change speed and error; do not call Float32 universally the GPU’s native precision. For π, the standard error is about 1.64/sqrt(n), as in module 1. This is not a guaranteed absolute-error bound. CPU/GPU RNGs may produce different samples even at the same n.

Time completed work

CUDA.@sync Ag * Bg   # wait for the GPU operation before stopping the timer

Python equivalent for a resident calculation:

torch.cuda.synchronize()
start = time.perf_counter()
Yg = Ag @ Bg
torch.cuda.synchronize()
seconds = time.perf_counter() - start

Warm up before repeated measurements. GPU operations can enqueue work and return before it finishes; an unsynchronized host timer can measure submission rather than completion. The first synchronization excludes earlier work; the second includes this product’s completion. Returning a result to the CPU can also synchronize, but state the timed scope explicitly.

A complete product needs two uploads, the product, and its result download.

▶ Script: cell “What the copy costs”. Historical rounded minimum timings include allocation for the transfer calls. Direction alone does not determine transfer cost; buffers, memory allocation and runtime state matter. 2×8.5+35+52 ≈104 ms is a derived estimate, not an observed complete-job time. Measure the complete path rather than summing independently timed minima.

Resident work and the complete job

# Inputs already on the GPU; result remains there
CUDA.@sync Ag * Bg

# Host inputs → upload → product → host result
matmul_to_host(A, B) = CUDA.@sync Array(CuArray(A) * CuArray(B))

Keep intermediate data on the GPU when possible; return the result the application requires.

▶ Script: cell “The matrix product, resident and complete”. Compare both scopes with CPU A*B using identical Float32 inputs. Check the returned matrix, not only the runtime. The function includes allocations, both uploads, the operation, synchronization and the download. A matrix-valued application cannot replace its required result by a scalar merely to avoid transfer.

Monte-Carlo π on the GPU

Generate, count and reduce on the device

function pi_gpu(n)
    x = CUDA.rand(Float32, n)
    y = CUDA.rand(Float32, n)
    inside = (x.^2 .+ y.^2) .<= 1f0
    return 4 * sum(inside) / n
end
  • The points are generated on the GPU, without uploading point vectors.
  • A library reduction returns one scalar to the host.

▶ Script: cell “6. Monte-Carlo π on the GPU”. The complete estimator includes allocations, random generation, comparison, reduction, synchronization and scalar return. The reduction is parallel; its final stages expose less parallelism. This is the module-3 local-count pattern implemented by library kernels. 1f0 is 1 represented as Float32.

Optional — coalescing

Neighboring threads, neighboring addresses

  • CUDA groups threads into warps of 32.
  • Neighboring addresses can be served by fewer memory transactions.
  • Scattered addresses can require more transactions.

CPU locality concerns a thread’s access sequence; coalescing also concerns addresses accessed by neighboring GPU threads.

This CUDA example concerns NVIDIA warps. Do not equate a warp with 32 CPU cores or assume that all divergent threads progress in strict lockstep. Map thread indices to the actual layout.

Coalescing: a controlled permutation

idx = CuArray(Int32.(((0:N-1) .* s) .% N .+ 1))
a[idx]   # same elements in a different order when gcd(s,N) = 1
Stride Historical time
1 2.24 ms
33 5.40 ms
1023 12.3 ms

▶ Script: cell “7. Optional — coalescing”. N=20 million; require a permutation so this does not merely reread a smaller subset. gcd(33,N)=gcd(1023,N)=1. This operation also reads the index array and writes an output. Identify all arrays before assigning the ratio to one cause.

Test a memory-traffic explanation

Compute the index in the kernel rather than loading an index array:

i = (blockIdx().x - 1) * blockDim().x + threadIdx().x
j = ((i - 1) * s) % n + 1
out[i] = a[j]

Historical stride-33 / stride-1 ratios: 2.4× with a[idx], 4.18× with computed indices.

Index arithmetic and allocation also change: this comparison does not isolate one effect.

▶ Script: cell “Test that explanation”. The output is still written contiguously. Nominally, source reads are one third of the gather’s bytes versus one half without an index array, but nominal bytes are not memory-transaction counts. Validate the permutation’s output too.
