The JIT warmup

A tale of two ships

The loop we will study

function mysum(x)
    s = zero(eltype(x))     # 0.0 here
    for i in eachindex(x)
        s += x[i]
    end
    return s
end
  • Pure Python, 10⁷ floats: ~0.5 s
  • Julia: a few ms
  • Same loop, same machine. Why the gap?

The experiment

  • Sum 10⁶ floats, 2000 calls, time each call
  • 5 variants: pure Python, numba @njit, numpy, Julia mysum, Julia sum

What happens on the very first call?

Warmup: the curves appear

Reading the curves

variant 1st-call spike plateau
pure Python 0 ~50 ms
numba @njit ~270 ms ~0.4 ms
numpy ≈ 0 ~0.2 ms
Julia mysum ~7 ms ~0.4 ms
Julia sum ~20 ms ~0.1 ms

Spike then fast (numba, Julia) · no spike (Python slow, numpy fast). Why?

Three ways to run code

  • Interpreted (CPython): re-examined at run time → instant start, slow
  • AOT (C, numpy): compiled before → fast, no warmup
  • JIT (Julia, numba): compiled on 1st call → fast after

The spike is the JIT compiling. Paid once.

Interpreted: each operation is re-examined at run time (bytecode visible with dis in the Python notebook). AOT = ahead-of-time, JIT = just-in-time. The JIT cost is amortized over later calls.

Don’t say “Python can’t specialize by type” — false since 3.11 (PEP 659): the adaptive interpreter rewrites a hot s += x into BINARY_OP_ADD_FLOAT. The point is that it specializes ONE bytecode and KEEPS the guard, inside the interpreter, on boxed objects. Julia specializes the whole function and deletes the guard. That’s why the 100× survives.

numpy: fast, but only inside

numpy.sum: the loop is compiled C.

  • Python for over a numpy array: slow again
  • Python: vectorize — push loops into numpy
  • Julia: your own loop is compiled too

A Python for loop over a numpy array is slow because each element crosses back into the interpreter. In Julia there is no such boundary.

Measuring properly

Pitfall 1: timing the compiler

g(x) = sum(abs2, x)
@time g(v)   # compile + compute
@time g(v)   # compute only

Discard the 1st call; measure the steady state.

▶ Script: cell “0. Getting started”, then “2. Measuring properly — compare the two timings”

The very first line of a session is slow for the same reason: everything it touches (here @btime and BenchmarkTools) gets compiled.

Pitfall 2: measuring only once

using BenchmarkTools
@btime     mysum($v)   # minimum
@benchmark mysum($v)   # distribution
  • Many runs, warmup dropped
  • $v plugs the value in: time mysum, not the global lookup (why: with dispatch)
  • Always $ before globals in @btime

@btime / @benchmark run the call many times and drop the warmup for you. Without $, we would also time the lookup of the untyped global variable v. Why an untyped global is slow: with dispatch, when the compiler cannot know the type.

Type specialization

One x + y, several machine codes

No single “x + y” instruction: it depends on the types.

x, y machine code for x + y
Int, Int add (integer)
Float64, Float64 vaddsd (float)
Float64, Int vcvtsi2sd + vaddsd (convert + add)

Julia: 1st call compiles a version for the concrete types, then reuses it. No type checks left → ≈ C.

Each entry in the table is one (or two) processor instructions. Picking the version from the types of ALL arguments is multiple dispatch — next module.

mysum: what to look for

vaddsd  xmm0, xmm0, [rcx + 8*rdx]
vaddsd  xmm0, xmm0, [rcx + 8*rdx + 8]
...
  • vaddsd = Scalar Double → 1 float / instruction
  • Always xmm0 → one accumulator: each + waits for the previous

sum: what to look for

@code_native sum(vc) is mostly a call; the work is in Base.mapreduce_impl:

vaddpd  ymm0, ymm0, [r8 + 8*r9 - 96]
vaddpd  ymm1, ymm1, [r8 + 8*r9 - 64]
vaddpd  ymm2, ymm2, [r8 + 8*r9 - 32]
vaddpd  ymm3, ymm3, [r8 + 8*r9]
  • vaddpd = Packed Double → 4 floats / instruction (SIMD)
  • 4 accumulators ymm0…ymm3 → 4 independent chains

Why not our loop?

Bet first: why can’t the compiler do this for our loop?

What we saw: the order of the additions

Warning

Float + is not associative: (a+b)+c ≠ a+(b+c). The compiler must keep our order → scalar.

sum allows reordering → vectorized.

@simd: permission to reorder

function mysum_simd(x)
    s = zero(eltype(x))
    @inbounds @simd for i in eachindex(x)   # ← @simd
        s += x[i]
    end
    return s
end

@inbounds: no bounds checks · @simd: may reorder +

variant time / call
mysum (scalar) 44 µs
mysum_simd (vaddpd) ~4 µs
Base sum 7.5 µs

Not magic: the algorithm (reordering → SIMD), not the language.
