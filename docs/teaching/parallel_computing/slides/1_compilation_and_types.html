Approach Loop execution Compilation

NumPy provides compiled operations; Julia and Numba also compile your own loops.

One explanation after the experiment. A Python loop over a NumPy array still executes in the interpreter. CPython also specializes interpreter instructions; that does not compile this whole loop to native code. Julia specializations may already be available; not every first call must compile. Measuring execution time

Pitfall 1: including compilation without saying so

g(x) = sum(abs2, x)
@time g(v)   # first call: may include compilation
@time g(v)   # warmed-up call

Report the first call separately from warmed-up calls.

▶ Script: cell “2. Measuring properly”. For a one-shot script, compilation is part of user-visible runtime. It is not noise to discard without stating the scope. The first call can also include library initialization, allocation and cache effects.

Pitfall 2: relying on one measurement

@btime     mysum($v)   # minimum across repeated measurements
@benchmark mysum($v)   # distribution
  • Record warmup, repetitions and the reported statistic.
  • $v supplies the input value to the Julia benchmark.
  • Python: timeit, or repeated perf_counter measurements.

▶ Script: cell “Read the timing distribution”. The minimum approximates a low-interference execution time; the median describes a typical observation. Report which one you use. BenchmarkTools performs warmup and repeated evaluations; explain globals in the dispatch module.

estimate_pi(n) = 4 * count_in_disk(n) / n
  1. How long does estimate_pi(1_000_000) take after warmup?
  2. How can we check a result that changes between runs?

▶ Script: cells “3. Monte-Carlo π” and “Timing the estimator”. Type inference, allocations and preparation for parallelism are not additional questions here. We focus on timing scope and correctness. The following slide separates two kinds of checks.

Two complementary checks

  • Counting logic: fixed points with a known count.
  • Estimator: error consistent with its standard error, approximately \(1.64/\sqrt{n}\).
x = [0.0, 0.5, 1.0, 1.0]
y = [0.0, 0.5, 0.0, 1.0]
# Three points satisfy x² + y² ≤ 1.

A statistical tolerance complements the code check; it does not replace it.

▶ Script: cells “Check the counting logic” and “Check the estimator”. Use the same inside_disk predicate in the random loop and the fixed-point check. With p = π/4, SE = 4 sqrt(p(1−p)/n). At n = 10⁶ it is about 0.00164. A single error can increase as n increases. A check at several standard errors can occasionally fail for a correct estimator, and passing it does not establish correctness. A fixed seed supports repeatability; an independently known count supports correctness.

Which block should we optimize?

Local speedup and whole-program speedup

A block takes a fraction \(f\) of the time and becomes \(s\) times faster:

\[\text{whole-program speedup} = \frac{1}{(1-f) + f/s}\]

Which change helps more?

  • A: 10% of the time, 10× faster.
  • B: 80% of the time, 2× faster.

Assume unchanged work and unchanged costs outside the block. A: 1.10×; B: 1.67×. Even an instantaneous A gives at most 1.11×. Reveal answers in the diagnostic debrief. The same model is used later for parallel work in Amdahl’s law.

Four rules for reliable comparisons

  1. Distinguish first-call and warmed-up times.
  2. Report the measurement protocol.
  3. Check the code and the statistical result.
  4. Measure whole-program speedup, not only the block.

Scalar and SIMD reductions

Scalar: one accumulator

vaddsd xmm0, xmm0, [a]
vaddsd xmm0, xmm0, [b]

One Float64 addition per instruction; a dependency chain.

SIMD: several accumulators

vaddpd ymm0, ymm0, [a]
vaddpd ymm1, ymm1, [b]

Four Float64 additions per instruction here; independent chains.

▶ Script: cells “Our loop’s assembly” to “The kernel sum calls”. Excerpts are schematic; register widths depend on the target. vaddsd is scalar double; vaddpd is packed double. sum’s work may be in Base.mapreduce_impl rather than its wrapper.

Addition order matters

Why does the compiler preserve the order of our floating-point reduction?

(1e16 + (-1e16)) + 1.0   # 1.0
1e16 + ((-1e16) + 1.0)   # 0.0

Floating-point addition is not associative. Reordering can change the result.

▶ Script: cell “Addition order matters”. Independent accumulators and SIMD reductions alter the addition order. This matters to the correctness specification; bitwise equality is not generally the appropriate check.

Allowing SIMD

function mysum_simd(x)
    s = zero(eltype(x))
    @inbounds @simd for i in eachindex(x)
        s += x[i]
    end
    return s
end

@simd permits reordering; @inbounds skips bounds checks.

Reference: 44 µs → ~4 µs. Check mysum_simd(vc) ≈ sum(vc).

▶ Script: cell “@simd: permission to reassociate”. Benchmark the same vc as in the previous table. Reordering the reduction enables SIMD and independent accumulators. The assertion is a check on this input; numerical tolerances must be justified for the application.
